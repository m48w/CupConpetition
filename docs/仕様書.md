# VELOCITY CUP 2026 大会運営Webアプリ仕様書

## 1. 概要

本システムは、フットサル大会「VELOCITY CUP 2026」の試合スケジュール、ライブスコア、順位表、トーナメント、管理者操作をブラウザーで確認・操作するための大会運営Webアプリである。

試合データは Cloudflare の Durable Object に保存し、同じ Worker の API 経由で読み書きする。変更は WebSocket で全端末へ即時に配信する（詳細は10章）。

## 2. 技術構成

- UI: React 18
- 言語: TypeScript
- ビルドツール: Vite
- ルーティング: React Router
- 実行環境: Cloudflare Workers（静的アセット配信と `/api/*`）
- データ保存: Durable Object `TournamentRoom` の SQLite
- 配信: WebSocket（Hibernation API）
- スタイリング: CSS
- 開発サーバー: Vite Dev Server（`@cloudflare/vite-plugin` で Worker と Durable Object をローカルの workerd 上で動かす）
- テスト: vitest（Worker 側は `@cloudflare/vitest-plugin` で workerd 上で実行）

ビルドコマンド:

```bash
npm run build
```

## 4. 大会データ仕様

### 4.0 オンライン登録

- 登録データは Durable Object SQLite の `registration_clubs`、`registration_teams`、`registration_members`、`registration_access`、`registration_verify_attempts` で管理する。
- クラブのロゴは既存の `logos` テーブルに保存し、クラブから参照する。
- 代表者登録画面はクラブ名、1つ以上のチーム名、代表者名、メールアドレス、電話番号を収集する。複数チーム参加を選ぶと「＋」でチーム名欄を追加し、同一クラブ分を一括申請する。電話番号は数字列へ正規化、メールアドレスはtrim後に小文字化する。
- メンバー登録は氏名と0以上の整数の背番号のみを収集する。年齢等、他の選手情報は収集しない。
- 登録チームは試合運営用 `teams`、試合、順位表には自動反映しない。管理者が後日試合枠へ割り当てる。

### 4.1 チーム

- グループ数: 8
- グループ識別子: A〜H
- 1グループのチーム数: 5
- 総チーム数: 40
- チーム情報は Durable Object の SQLite `teams` テーブルに保存し、初回作成時に既存の40チームを登録する。
- チームはID、表示順、チーム名、グループ、表示色、任意のロゴIDを持つ。
- ロゴ画像の実体は SQLite `logos` テーブルに保存し、チームの `logo_id` から参照する。画像データはBase64文字列で保持する。
- 現在の初期チーム名（Team1〜Team40）とグループ・色は `src/features/tournament/data.ts` の定義から登録する。
- 試合運営用の初期40チームと、オンライン登録フォームの参加受付レコードは別データとして保存する。登録内容を固定の試合枠へ自動反映しない。
- オンライン登録フォームからクラブ・参加チームを登録できる。クラブ単位で複数の参加チームを持てる。チーム登録は即時受付とし、現行仕様に登録締切は定めない。
- 登録チーム名の完全一致は重複登録として拒否する。同じクラブ名でも異なるチーム名は登録できる。
- 登録チームは既存連絡先とメールアドレス・電話番号の両方が一致した場合のみメンバー登録できる。同一連絡先を複数チームで共有する場合は、本人確認後に対象チームを選択する。
- メンバーの本人確認セッションはサーバー側Cookieで管理し、1時間で失効する。接続元IPごとに15分あたり5回まで照合できる。
- メンバーは1チーム最大11名、同一チーム内の背番号重複不可。2026-12-12 23:59:59 JSTまで登録可能で、サーバー側で締切を判定する。代表者による登録済みメンバーの編集・削除は不可。
- 代表者登録ではPNG・JPEG・WebP（最大1 MB）のクラブロゴを必須でアップロードする。ロゴは同クラブの登録チームで共有し、2チーム目以降の登録では上書きしない。ロゴ変更はSuper Adminのみ許可する。
- ロゴ選択時は登録フォーム内に画像プレビューを表示する。複数チームの一括申請ではロゴは1つだけ選択し、同クラブの各チームで共有する。
- 登録情報および連絡先を含む管理一覧もSuper Admin専用とし、Sub-adminには公開しない。
- チーム名の左側にロゴ画像を表示する。チームにロゴが登録されていない場合、または画像を取得できない場合は、チーム色とチーム名の頭文字を使ったバッジを表示する。

### 4.2 グループステージ

- 1グループあたり10試合。
- 全8グループで80試合。
- 試合IDは `G-{Group}-{番号}` 形式。
- グループ試合はCourt 1〜3に割り当てる。ただしCourt 3は12:15から使用する。
- 開始時刻は2026-12-20 09:00（Asia/Tokyo）から15分刻みで31スロット。12:15より前のスロットは最大2試合（Court 1・2）、12:15以降は最大3試合（Court 1〜3）を割り当てる。

### 4.3 ノックアウト

- Round of 16
- Quarter-finals
- Semi-finals
- Final
- ノックアウト合計15試合。
- 3位決定戦は設けない。
- 試合時間（ハーフタイム込み）:
  - Round of 16: 18分
  - Quarter-finals（ベスト8）・Semi-finals（ベスト4）: 7分ハーフ・ハーフタイム1分の計15分
  - Final: 10分ハーフ・ハーフタイム3分の計23分
- グループステージ終了後、および各ラウンドの間に18分の休憩を空けて開始する。各ラウンドの開始時刻と試合数は4.4を参照。

### 4.4 大会スケジュール

全95試合を2026-12-20（日）09:00から連続開催し、19:59に終了する。09:00〜12:15はCourt 1・2の2コート、12:15以降はCourt 3を加えた3コートを使う。

| ラウンド | 時刻 | 試合数 |
|---|---|---|
| グループステージ | 09:00 〜 16:45（15分×31スロット。12:15より前の13スロットで26試合、以降の18スロットで54試合） | 80 |
| Round of 16 | 17:03 / 17:21 / 17:39（各18分） | 8 |
| Quarter-finals | 18:15 / 18:30（各15分） | 4 |
| Semi-finals | 19:03（15分） | 2 |
| Final | 19:36 〜 19:59（23分） | 1 |

制約は次の3つである。

- 同一コートで試合の時間帯が重ならない。
- 同一チームの試合間隔を15分以上空ける。
- Court 3には12:15より前の試合を入れない。

いずれも `src/features/tournament/schedule.test.ts` で検証している。

## 9. 管理者仕様

### 9.1 アカウントとログイン

| ユーザー名 | 役割 | 担当 | パスワード |
|---|---|---|---|
| `superadmin` | Super-admin | 全コート | Secret `SUPERADMIN_PASSWORD` |
| `subadmin1`・`subadmin2` | SubAdmin | Court 1 | Secret `SUBADMIN_PASSWORD`（6人共通） |
| `subadmin3`・`subadmin4` | SubAdmin | Court 2 | 同上 |
| `subadmin5`・`subadmin6` | SubAdmin | Court 3 | 同上 |

- `/superadmin` はパスワードだけ、`/subadmin` はユーザー名とパスワードを入力する。ユーザー名の大文字小文字と前後の空白は区別しない。
- ログインに成功すると、サーバーが署名した `session` Cookie（HttpOnly・Secure・SameSite=Strict、12時間）を発行する。ログイン状態はブラウザーに保存しない。
- 同じユーザー名で5回続けて失敗すると、60秒間ログインできない。失敗回数は大会IDに関係なく、固定の Durable Object（名前 `auth`）で数える。
- 「Sign out」でログアウトする。
- ヘッダーの管理リンクは開発環境でのみ表示する。本番では `/superadmin`・`/subadmin` を直接開く。
- 開発環境のパスワードは `.dev.vars`（見本は `.dev.vars.example`）。本番は `wrangler secret put` で設定する。
- セッションは12時間で切れるため、大会当日の朝にログインすること（前夜のログインは大会中に失効する）。
- Cookie は `Secure` 属性付きのため、`http://<LAN IP>` で開発サーバーにスマートフォンからアクセスしてもログイン状態を維持できない。`localhost` か https トンネル経由でテストすること。

### 9.2 権限

| 操作 | 未ログイン | SubAdmin | Super-admin |
|---|---|---|---|
| 閲覧（`GET /api/state`・WebSocket） | 可 | 可 | 可 |
| 試合の得点・状態の変更 | 不可（401） | 担当コートの試合のみ（他は 403） | 全試合 |
| Seed knockout teams・Reset all matches | 不可（401） | 不可（403） | 可 |

SubAdmin の画面には担当コートの試合だけを表示し、Seed knockout teams と Reset all matches の区画は表示しない。

### 9.3 試合操作

選択した試合の状態（Not started / ● LIVE / Ⅱ PAUSED / ■ Finished）とタイマーを、試合操作の上に大きく表示する。試合選択リストにも、未開始以外の試合には状態を併記する。

Super-admin と SubAdmin は選択した試合に対して以下を実行できる。

- ホーム・アウェイスコアを1点増減。押すたびに即時保存し、全端末へ反映する。未開始の試合では操作できない。
- 操作ボタンは状態に応じて表示を切り替える。

| 現在の状態 | 表示するボタン | 動作 |
|---|---|---|
| `SCHEDULED` | ▶ Start match | `LIVE`にし、タイマーを0から開始する |
| `LIVE` | Ⅱ Pause | `PAUSED`にし、経過時間を保存してタイマーを止める |
| `LIVE` / `PAUSED` | ■ Finish match | `FINISHED`にし、最終の経過時間を保存する |
| `PAUSED` | ▶ Resume | `LIVE`に戻し、止めた時点の続きからタイマーを進める |
| `FINISHED` | なし | — |

### 9.4 大会運営操作

Super-admin 画面の「SUPERADMIN SETUP」には、選択中の試合とは別に大会全体に対する操作がある。

- **Seed knockout teams**: グループステージの順位からRound of 16の対戦相手のみを埋める。試合時刻・Courtは変更しない。
- **Schedule check**: 現在の全試合についてコートの二重予約の有無と最終試合の終了時刻を実際に計算して表示する（例: `ⓘ Schedule check: 95 matches, no court clashes, finishing 19:59.`）。コート重複がある場合は該当する試合IDの組を表示する。
- **↺ Reset all matches**: 全95試合をスコア・タイマー未設定の初期状態に戻す。ボタンを押すと確認メッセージが表示され、「Yes, reset」で実行、「Cancel」で取り消す。通常のリセット手段はこのボタンである（詳細は10章）。

## 10. データ同期仕様

試合・チーム・ロゴデータは Cloudflare の Durable Object `TournamentRoom`（名前 `main` の1インスタンス）の SQLite を唯一の正本とする。ブラウザーは Worker の `/api/*` 経由で操作し、更新後の試合とチーム情報は WebSocket で全端末へ配信される。既存の2026-09-26開催日を2026-12-20へ一度だけ移行するストアマイグレーションを行う。旧 `TempServerData/matches.json` は使用せず、削除済み。

SQLite の `teams` テーブルには試合運営用チームID、表示順、チーム名、グループ、表示色、任意のロゴIDを保存する。オンライン受付用クラブ・チーム・メンバーは別の登録テーブルで管理する。`logos` テーブルにはロゴID、Content-Type、Base64形式の画像データ、作成日時を保存する。受付時の必須クラブロゴアップロード、およびSuper Adminによるロゴ変更を提供する。

### 10.1 API

| メソッド | パス | 権限 | 用途 |
|---|---|---|---|
| `POST` | `/api/login` | 誰でも | ログイン。成功すると `session` Cookie を発行 |
| `POST` | `/api/logout` | 誰でも | `session` Cookie を削除 |
| `GET` | `/api/session` | 誰でも | ログイン中の利用者（`{"session": null}` なら未ログイン） |
| `GET` | `/api/state` | 誰でも | 全チーム・全試合とversionを返す |
| `GET` | `/api/logos/:id` | 誰でも | IDで指定したチームロゴ画像を返す（存在しない場合は404） |
| `GET` | `/api/ws` | 誰でも | WebSocket。接続時に全state、以後は更新のたびに配信 |
| `PATCH` | `/api/matches/:id` | Super-admin・担当コートの SubAdmin | 1試合の部分更新 |
| `PUT` | `/api/matches` | Super-admin | 全置換 |
| `POST` | `/api/reset` | Super-admin | 全試合を未開始へ戻す |

変更系（`POST`・`PUT`・`PATCH`・`DELETE`）は `content-type: application/json` が必須で、違えば `415`（`UNSUPPORTED_MEDIA_TYPE`）を返す。未ログインは `401`（`UNAUTHENTICATED`）、権限なしは `403`（`FORBIDDEN`、担当外コートは `WRONG_COURT`）。ログインの失敗は `401`（`INVALID_CREDENTIALS`）、試行制限中は `429`（`TOO_MANY_ATTEMPTS`、`Retry-After` ヘッダー付き）、Secret 未設定は `500`（`AUTH_NOT_CONFIGURED`）。

### 10.2 更新の流れ

スコアや状態の編集など、試合単位の操作は `PATCH /api/matches/:id` として送られる。Seed knockout teamsは `PUT /api/matches`、Reset all matchesは `POST /api/reset` を使う。Durable Object は該当の試合だけを書き換え、`version` を1つ増やして保存し、接続中の全 WebSocket へチームと試合を含む `{"type":"state","state":...}` を送る。クライアントは10秒ごとに `ping` を送り、サーバーは `pong` を返す。

ロゴ画像は `GET /api/logos/:id` で取得し、画像のContent-Typeと `X-Content-Type-Options: nosniff` を返す。画像を取得できない場合、クライアントは頭文字バッジにフォールバックする。

`PATCH` で変更できるのは `status`、`homeScore`、`awayScore`、タイマー項目、PK戦項目のみである。試合ID、Round、Court、開始予定時刻、対戦チームは変更できない。

存在しない試合IDを指定した場合は `404` で `{"error": "unknown match: ...", "code": "UNKNOWN_MATCH"}` を返す。変更できないフィールドを含めた場合は `400` で `{"error": "field is not patchable: court", "code": "FIELD_NOT_PATCHABLE"}`、値の型が不正な場合は `400` で `INVALID_FIELD_VALUE`、`PUT` で試合IDが重複している場合は `400` で `INVALID_MATCHES` を返す。リクエストボディがJSONとして解釈できない場合も `400` を返す。

### 10.3 保全

- Durable Object はリクエストを1つずつ処理するため、並行更新による取りこぼしは起きない。
- 全置換とリセットは1つのトランザクションで書き込み、途中で失敗しても半端な状態を残さない。
- 試合データはメモリに持たず、常に SQLite から読む。Durable Object が休止・退避されても内容は失われない。

### 10.4 接続断

サーバーへ接続できない場合、画面上部に切断バナーを表示し、管理操作を無効化する。最後に取得したデータは表示したままにする。クライアントは1秒から最大10秒まで間隔を延ばしながら自動で再接続し、再接続時に全stateを受け取って同期する。25秒間何も届かない接続は切れたものとみなして張り直す。

## 11. 非機能・制約

- 本番は Cloudflare Workers（無料プランを想定）で動かす。Workers と Durable Objects の無料枠は1日10万リクエストで、WebSocket の接続確立が1リクエスト、サーバーからの送信は無料。
- 複数端末・複数ユーザーでの同時編集をサポートする。同一フィールドを同時に変更した場合は後着信が優先される（明示的なロックや競合解決は段階3で入れる）。
- パスワードと署名鍵は Cloudflare の Secrets に置き、コードとビルド成果物には含めない。

## 15. オンラインチーム・メンバー登録

### 15.1 データの分離

オンライン受付は、クラブ（Club）、大会参加チーム（Registration Team）、メンバー（Team Member）からなる。クラブは複数の登録チームを持ち、ロゴと代表者連絡先を共有する。受付データは `registration_clubs`、`registration_teams`、`registration_members` 等のSQLiteテーブルで管理する。初期40チームの試合運営データとは別であり、登録によって試合、順位表、固定の参加枠を自動変更しない。Teams画面では受付済みチームをロゴとチーム名だけのカードで公開する。カードを選ぶとチーム名、ロゴ、登録済みメンバー名・背番号を表示する。代表者の連絡先は公開しない。試合運営チームの一覧とは別セクションにする。

### 15.2 チーム登録フォーム

登録画面のURLは `/registration/20261220/` を基点とする。画面ルートは `/`（登録フォーム）、`/complete`（受付完了）、`/verify`（代表者確認）、`/members`（メンバー登録）。スマートフォンを含む画面幅に対応し、登録ヘッダーに大会ロゴを表示し、ロゴ選択後はクラブロゴのプレビューを表示する。

| 項目 | 必須 | 仕様 |
|---|---|---|
| クラブ名 | はい | 120文字以内 |
| 大会参加チーム名 | はい | 通常は1件。複数チーム参加を選択すると「＋」で入力欄を追加 |
| 代表者名 | はい | 120文字以内 |
| メールアドレス | はい | 形式を検証し、照合用に正規化 |
| 電話番号 | はい | 形式を検証し、数字列へ正規化 |
| クラブロゴ | はい | PNG、JPEG、WebP。1 MB以下。1申請につき1画像 |

1回の申請で登録できるチーム名は1〜40件。チーム名は申請内および大会内で重複不可。複数チーム申請は一括処理し、検証に失敗した場合は全チームを登録しない。各チームは独立したIDを持つ。同じクラブのロゴは共有され、既存ロゴは後続申請の画像で上書きしない。既存ロゴの変更はSuper Adminのみ可能。

登録完了画面には受付チームを表示する。登録は即時受付で、チーム登録自体に締切は設定しない。

### 15.3 代表者確認とメンバー登録

登録完了後、代表者は登録時のメールアドレスと電話番号の両方で本人確認する。照合はサーバー側で行い、成功すると1時間有効のHttpOnly・Secure・SameSite=Strict Cookieを発行する。同一接続元IPからの照合は15分間に最大5回。連絡先をURLに含めない。照合に失敗しても、登録済み連絡先の存在を推測できる情報を返さない。

1チームにつき登録できるメンバーは最大11人。入力項目は氏名と0以上の整数の背番号のみ。登録画面には常に11行を表示し、Player NameとBack Numberを横並びにする。登録済み人数を差し引いた空き枠の行だけ入力できる。未登録の全員を入力し、一度の送信でまとめて登録できる。背番号は同一チーム内で重複不可、別チーム間では重複可。人数、重複、登録期限はサーバーでも検証し、バッチ内に不正な行があれば全件を登録しない。代表者は登録済みメンバーを編集・削除できない。

メンバー登録期限は2026年12月12日（土）23:59:59 JST。期限後の追加はサーバー側で拒否する。期限後の特例登録と誤登録の訂正手順は本仕様の対象外。

## 17. 大会別データと初期状態

- `/test/` は確認用大会で、既存のサンプル40チーム・95試合を表示する。
- `/20261220/` は本番大会で、大会IDごとに独立した Durable Object SQLite を使い、初期状態はチーム0件・試合0件とする。
- APIが受け付ける大会IDは `20261220` と `test` の2つだけとする（`worker/index.ts` の `ALLOWED_TOURNAMENT_IDS`）。それ以外の大会IDは `400 INVALID_TOURNAMENT_ID` を返し、新しい Durable Object を作らない。大会を追加するときはこの一覧も更新する。
- アプリの初回表示はサーバーからstateを受け取るまで空配列を表示し、サンプルを先に描画しない。
- 登録、チーム、試合、ロゴ、本人確認情報は大会IDの領域内で保存する。大会IDは起動時にページURL（暗号化URLの場合は復号したルート）から一度だけ決め（`setTournamentId`）、APIとWebSocketへ渡す。アドレスバーが `/u/...` に変わった後に `window.location` から大会IDを読み直さない。
- 従来のDurable Object名 `main` に保存済みのデータは削除せず、新しい大会IDへ自動移行もしない。新しい大会URLでは新しい空データベースを使用する。

Super Adminの管理画面では現在の大会IDを表示し、次の操作を行える。

- 大会の初期化：現在の大会のチームと試合を空にする。登録受付情報は削除しない。
- チーム追加：チーム名、グループ（A〜H）、表示色を指定する。
- チーム編集・削除：試合開始前に操作できる。変更すると既存の試合一覧を空にし、変更中のチーム名やグループを参照する試合が残らないようにする。
- スケジュール作成：8グループに各5チーム、合計40チームが登録された後、現在のチーム一覧から試合を作成する。開始済み試合がある場合、チーム変更と再生成は拒否する。

### 17.1 ローカルSQLiteの確認

開発WorkerのDurable Object SQLiteは `.wrangler/state/v3/do/velocity-cup-TournamentRoom/` に保存される。大会ごとのSQLiteファイル名はDurable Object IDから生成される。実際のファイル名を確認して、読み取り専用で開く。

```bash
for DB_FILE in .wrangler/state/v3/do/velocity-cup-TournamentRoom/*.sqlite; do
  TOURNAMENT_ID=$(sqlite3 -readonly "$DB_FILE" "SELECT tournament_id FROM tournament_info WHERE id = 1;" 2>/dev/null) || continue
  printf '%s %s\n' "$TOURNAMENT_ID" "$DB_FILE"
done

sqlite3 -readonly ".wrangler/state/v3/do/velocity-cup-TournamentRoom/<大会のSQLiteファイル>" ".tables"
sqlite3 -readonly ".wrangler/state/v3/do/velocity-cup-TournamentRoom/<大会のSQLiteファイル>" "SELECT id, name, group_id, color FROM teams ORDER BY position;"
sqlite3 -readonly ".wrangler/state/v3/do/velocity-cup-TournamentRoom/<大会のSQLiteファイル>" "SELECT count(*) AS teams FROM teams; SELECT count(*) AS matches FROM matches;"
```

開発中は`/test/`のチーム一覧とSuper Admin管理画面からもstateを確認できる。本番環境のSQLiteファイルはCloudflare側に保存され、ローカルの`.wrangler`フォルダーにはない。本番の大会チームは該当大会URLのSuper Admin画面で確認する。

大会管理APIはすべてSuper Admin専用とする。`GET /api/state` はその大会のチーム・試合stateを返す。`POST /api/teams`、`PATCH /api/teams/:id`、`DELETE /api/teams/:id` でチームを管理し、`POST /api/initialize` で大会のチーム・試合を空にし、`POST /api/schedule` で40チームのスケジュールを作成する。APIの大会IDは画面URLから決定し、別大会のstateを更新しない。
