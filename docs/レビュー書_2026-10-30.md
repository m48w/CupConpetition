### 結果のまとめ

## 2. 良い点

- **デザイン**：ダークテーマで全ページに統一感がある。カウントダウンも正しく動く。
- **エラー**：どのページでもコンソールにエラーが出ていない。
- **フォーム**：登録フォームに `required`・`autocomplete`・`maxLength` がきちんと付いている。
- **CSRF対策**：データを変えるリクエストは `application/json` だけ受け付ける。
- **ロゴのアップロード**：Content-Type だけでなく、ファイルの先頭バイト（マジックナンバー）も確認している。
- **パスワード比較**：`crypto.subtle.timingSafeEqual` を使い、時間差で推測されない。
- **秘密情報**：`.dev.vars` は `.gitignore` に入っている。
- **テスト**：テストが多く（修正前140件）、安心して修正できる。

## 3. 悪い点（見つかった問題）

### 3.1 重大（今回修正済み）

#### (1) 大会IDが「u」になり、データが別の部屋に保存される

- **症状**：ロゴ取得の通信が `?tournamentId=u` になっていた。`tournamentId=20261220` でチーム一覧を取ると0件だった。
- **原因**：`src/config.ts` の `getTournamentId()` が毎回 `window.location.pathname` を読んでいた。URL暗号化でアドレスバーが `/u/<token>` に変わると、先頭の `u` を大会IDとして使っていた。
- **影響**：全API通信の `x-tournament-id` ヘッダー、WebSocketの再接続、ロゴURL、管理画面の大会IDが「u」になる。サーバーは形が正しいIDなら何でも受け付けていたため、`u` という別の Durable Object にデータが保存されていた。

#### (2) ログイン回数制限をすり抜けられる

- **症状**：なし（コードを読んで発見）。
- **原因**：ログイン失敗回数を大会IDごとの Durable Object に保存していた。大会IDはクライアントが送る `x-tournament-id` で決まる。
- **影響**：`x-tournament-id` を変えるだけで、パスワードを何回でも試せる。セッションCookieは全大会で使えるので、どこかで当たれば管理者になれる。メンバー登録の本人確認（メール＋電話）の回数制限も同じ問題があった。

### 3.4 英語のわかりやすさ

全体的に短くてわかりやすい。英語が少しわかる人向けには、次の所を直すとよい。

| 今の英語 | 問題 | おすすめ |
|---|---|---|
| WORLD CUP KNOCKOUT | ワールドカップではないので誤解される | Knockout stage |
| 15 slots | 「slots」が伝わりにくい | 15 matches |
| 0 competition · 3 registered | 文法の誤り | 0 competing · 3 registered |
| P / GD / PTS | サッカーをよく知らないとわからない | Played / Goal diff. / Points（または説明を付ける） |
| R16-1 と Winner M1 | 名前の付け方がそろっていない | Winner R16-1 にそろえる |
| チーム登録 / メンバー登録 / ← 大会アプリに戻る | 英語のサイトに日本語が混ざっている | Register team / Register members / Back to tournament |

### 3.5 確認が必要なこと

- `GET /api/registration/teams` は、ログインしなくてもメンバーの名前と背番号を返す。公開してよいか確認する（未成年の選手がいる場合は特に）。

## 4. 修正したこと

### 4.1 大会IDの決め方（画面側）

| ファイル | 変更 |
|---|---|
| `src/config.ts` | 大会IDを起動時に一度だけ決めて覚える `setTournamentId()` を追加。`/u/...` からは大会IDを読まない `parseTournamentId()` を追加。`getTournamentId()` は引数なしなら覚えた値を返す |
| `src/main.tsx` | 起動時（`__APP_ROUTE__` から復号ルートを読んだ後）に `setTournamentId()` を呼ぶ |
| `src/utils/http.ts` | `window.location.pathname` を読むのをやめ、`getTournamentId()` を使う |

### 4.2 大会IDの制限とログイン回数（サーバー側）

| ファイル | 変更 |
|---|---|
| `worker/index.ts` | 大会IDを `ALLOWED_TOURNAMENT_IDS`（`20261220`、`test`）だけに制限。それ以外は `400 INVALID_TOURNAMENT_ID` |
| `worker/index.ts` | `POST /api/login` は常に固定の Durable Object（`auth`）で処理し、失敗回数を1か所で数える |

大会IDが2つに限られたので、本人確認の回数制限のすり抜けもほぼできなくなった。

### 4.3 テスト

| ファイル | 追加したテスト |
|---|---|
| `src/config.test.ts`（新規） | 通常パスから大会IDを読む／`/u/...` から「u」を読まない／起動時のIDを返す／ロゴURLに正しいIDが付く |
| `worker/api.test.ts` | 許可外の大会ID（`u`、`other-room`）に400を返す／大会IDを変えてもログインがロックされる |

### 4.4 ドキュメント

- `docs/仕様書.md`：大会IDの制限、大会IDの決め方、ログイン失敗回数の保存場所を追記。

### 4.6 デプロイ時の注意

- これまで「u」の部屋に保存されていたデータ（テスト用の3チーム）は、デプロイ後は表示されない。テスト用のため移行しない。
- 管理画面で設定した内容も「u」に入っていた可能性がある。表示がおかしければ再設定する。
